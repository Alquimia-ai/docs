A **shield** is a registered check that scores content and reports a verdict. Open **Shields**
in the sidebar to register one. You register it once, then attach it where it should run:

- to an **agent**, where it screens each user message before the agent answers ([Pre-processor](/platform/agent-creation/pre-processor));
- to a **tool**, where it screens every result the tool returns ([Tools](/platform/tools/overview), **Shields** tab);
- to a **knowledge base**, where it screens every passage retrieved from it ([Knowledge](/platform/knowledge/overview), **Shields** tab).

The shield holds *how* to score. *What to do* with the score (observe, flag, block, threshold,
label) is set wherever the shield is attached, so one shield can block in one place and only be
logged in another.

## Shield types

| Type | What it runs | You configure |
|------|--------------|---------------|
| **LLM sentinel** | A registered model with its own system prompt and structured verdict. | Model, system prompt, structured output, extra connector parameters. |
| **Hugging Face text classifier** | A hosted sequence-classification model scoring the whole message. | Endpoint URL, token, input template, label map. |
| **Hugging Face token classifier** | A hosted NER / token-classification model tagging spans (e.g. PII). | Endpoint URL, token, input template, label map. |
| **OpenVINO text classifier** | A sequence classifier on an OpenVINO model server. | Endpoint URL, token, tokenizer model, input template, label map. |
| **OpenVINO token classifier** | A token classifier on an OpenVINO model server. | Endpoint URL, token, tokenizer model, input template, label map. |
| **Prompt-injection heuristic** | Built-in English keyword patterns; no endpoint. | Heuristic weight and base score (optional). |

The type is fixed once the shield is registered.

<Warning>
  The prompt-injection heuristic only catches blatant English phrasing and is easy to
  paraphrase around. Treat it as a cheap first filter and pair it with a model-backed shield
  where injection resistance matters.
</Warning>

### Classifier fields

- **Endpoint URL** — the inference endpoint. Like the token, it is stored in the vault, never
  in the shield itself.
- **URL reference** — the vault key that holds the URL. Leave it blank and the URL is stored
  under a key of its own for this shield (`SHIELD_<ID>_URL`). Set it to share one endpoint
  between shields, e.g. `SHIELDS_PROVIDER_URL`. When you edit a shield, the URL field is
  empty: leave it blank to keep the stored URL, or enter a new one to replace it.
- **Token reference** — the vault key holding the endpoint's bearer token (default
  `SHIELDS_PROVIDER_API_KEY`). Enter the value next to it; it goes to the vault, never into the
  shield. Leave the reference blank for an open endpoint.
- **Label map** — the model's label ids mapped to names, e.g. `LABEL_1` → `toxic`. Policies
  target a label by its name.

### LLM sentinel memory

An LLM sentinel judges one message at a time. It never reads the conversation history and keeps
no long-term memory. This is fixed, not configurable: Studio writes it on every save.

## Adding an LLM sentinel

Click **Add Shield** and keep the type **LLM sentinel**:

{/* screenshot: sentinel-add-form */}

**Profile section** — defines what the sentinel does:
- **System Prompt** — instructions for the sentinel's LLM. E.g.: *"You are a content moderator. Classify the following user input as `safe` or `unsafe`. Return only the classification label."*

**Config section** — which model powers the sentinel:
- References a model registered under **Models**

**Structured Output** — the shape of the sentinel's verdict, as a JSON schema:

```json Toxicity verdict
{
  "title": "toxicity",
  "type": "object",
  "properties": {
    "is_toxic": { "type": "boolean" },
    "category": { "type": "string" }
  },
  "required": ["is_toxic"]
}
```

Paste the schema itself; Studio wraps it for the runtime. A structured verdict is what
empathy rules compare against, so prefer booleans and short labels over prose.

**Conditions section** — what happens based on the sentinel's output:

{/* screenshot: sentinel-condition-builder */}

The visual condition builder writes the expression an empathy rule evaluates against this
sentinel's verdict, such as `is_toxic == True` or `category == 'billing'`.

<Note>
  Sentinels run before the main agent, and every user message waits for them to finish. Use
  small, fast models (7B or smaller) for classification to keep latency low.
</Note>

## Using shields in agents

Once a shield is registered, it becomes available under **Pre-processor** during agent
creation. Assign as many as you need: each evaluates the message and publishes its verdict
under its own name.

With the default **Observe** action a shield records its verdict without refusing the request.
Set the agent's policy to **Block**, or pair the shield with an empathy rule, to change what the
user sees.

Agents reference the sentinel, so editing its prompt, model or output schema reaches every
agent that uses it. What each agent does with the verdict stays with the agent: an agent whose
specification was set to flag or block keeps that setting when you save it in Studio. A
sentinel that an agent still uses cannot be deleted.

See [Pre-processor](/platform/agent-creation/pre-processor) for how to assign sentinels to agents and act on their verdicts.
