---
title: "Secrets"
description: "How credentials are defined, scoped, resolved and distributed — and why Studio prefers the platform's default keys."
---

A secret has two parts:

- A **definition** in the workspace registry: its key, scope, type, whether it is required, and whether users hold their own values. Definitions travel with the workspace when it is published.
- One or more **values** in the vault. Values never leave the vault through Studio: they are write-only, and Studio shows whether a value resolves, never the value itself.

Configuration never holds a credential. A field that needs one holds a reference, `{"$secretRef": "RESPONSE_PROVIDER_API_KEY"}`, which the runtime resolves when the agent runs.

## Platform default keys

Every credential field in the platform already has a default definition: model connectors read `RESPONSE_PROVIDER_API_KEY` and `RESPONSE_PROVIDER_BASE_URL`, speech providers `TTS_PROVIDER_API_KEY` and `STT_PROVIDER_API_KEY`, shields `SHIELDS_PROVIDER_URL` and `SHIELDS_PROVIDER_API_KEY`, channels their own (`WHATSAPP_ACCESS_TOKEN`, `SLACK_ACCESS_TOKEN`, …).

Studio uses these keys by default. A field that references its default key needs no custom definition, so:

- a published workspace carries fewer secret definitions, and
- a workspace pulled from Discover asks for values under the same well-known names everywhere.

Use a **custom key** only when one workspace needs two different values for the same kind of field — two model providers with different API keys, for example. A custom key is registered as its own definition and published with the workspace.

<Note>
  MCP servers keep one key pair per server (`MCP_<NAME>_URL`, `MCP_<NAME>_CREDENTIALS`): a registered tool is shared by every agent that uses it, while the platform's MCP defaults hold one value per agent.
</Note>

## Scope

The scope decides where the value lives and who shares it.

| Scope | Studio label | Value |
|-------|--------------|-------|
| `local` | Agent | One per agent, set in that agent's **Secrets** section. |
| `shared` | Workspace | One for every agent in the workspace. |
| `global` | Deployment | One shared by every workspace of the runtime. |

Writing a value never changes a secret's scope: Studio always sends the definition already registered (or the platform's, for a default key).

## Who can change what

| Change | Role |
|--------|------|
| Create an **Agent** or **Workspace** secret, or set its value | Editor and above |
| Create a **Deployment** secret, or set its value | Platform admin |
| Define a **User scoped** secret, or set its default value | Platform admin |
| Set your own value of a User scoped secret | Anyone |
| Delete a secret | Same as setting its default value |

Referencing an existing secret from a model, tool, shield or voice provider takes only what creating that element takes. Forms offer only what your role allows.

## User scoped secrets

A **User scoped secret** lets each user store their own value — a personal API token for a tool, say. When the runtime knows who is chatting, it resolves such a secret from that user's value **only**: it never falls back to the workspace default, so nobody's credential is used on someone else's behalf. The default is still used when no user is involved.

Users manage their own values in the [My credentials](/platform/security#my-credentials) tab of **Secrets**.

## Resolution status

Studio asks the runtime for everything an agent needs: the secrets in its own configuration and
those read by the model, tool, voice provider and shield registrations it references. Each key
is checked on its own, so every problem shows at once:

- **Resolves** — a value is there.
- **Optional, empty** — no value, but the secret is not required, so it resolves empty. The agent
  runs; whatever reads it (an MCP server's credentials, say) gets nothing.
- **No value** — the secret is required, or it is per-user and you have no value of your own.
- **Not registered** — no definition where one is needed. A registration reads only registered
  keys, platform defaults included.

<Note>
  The check needs runtime `0.7.0` or later. See
  [Versions and Compatibility](/reference/compatibility#what-needs-runtime-0-7-0).
</Note>

## Setting values while trying an agent

**Try Me** checks the agent before the first message. When something does not resolve, it lists
every missing secret instead of the chat, and where each is read ("Model GPT-4o", "Tool Linear").
A value typed there goes where the agent reads it:

- an **Agent** secret, to the agent being tried;
- a **Per-user** secret, to you — your chats never fall back to the workspace default;
- anything else, to the workspace.

For a key with no definition yet, choose where its value lives and whether each user sets their
own; a platform default key keeps the platform's. **Try anyway** opens the chat regardless. If a
message later fails on a secret, the list comes back.

The **Try Me** button shows how many credentials are missing.

## The agent's Secrets section

A saved agent's editor has a **Secrets** section (`?tab=secrets`) with the same list, without
opening Try Me. It reflects the saved agent, so save your changes first. It is where an **Agent**
value belongs: model, tool, shield and voice forms set **Workspace** and **Deployment** values
themselves, but not one that differs per agent.

## Publishing

Publishing refuses a workspace whose registered definitions are not used by any agent or registration. Delete unused definitions under [Secrets](/platform/security#secrets) before publishing.
